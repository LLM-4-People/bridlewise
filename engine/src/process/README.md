# Process

The process layer: the pinned-process profile (the declared, content-hashed executables a run is permitted to spawn) and the one reader of process facts (procfs, liveness).

## What each file does

- `environment-projection.ts` — THE one projection of an environment for a child process: `MINIMAL_CHILD_ENVIRONMENT`, `COMMAND_ENVIRONMENT` (a model-run command: + HOME and the proxy), `SYSTEMD_RUN_ENVIRONMENT`, `PROXY_VARIABLES` (the platform's read order, which the outbound door uses), `projectEnvironment` (proxy values forwarded without userinfo) and the ONE allowlist entry rule (`environmentAllowlistEntryRefusal`, `ENVIRONMENT_ALLOWLIST_ENTRY`: no bare `*`, never the harness's own `HARNESS_*` namespace nor a prefix of it). Used by the engine's command tool, the long-task runner, the MCP stdio servers and their credential allowlist, and the server's subprocess environment.
- `live-network.ts` — the one live-network opt-in of a test run: `liveHostsUnderTest` (the root policy's `verification.networkUnderTest.liveHosts` when the run's environment sets its consent variable to "1", none otherwise; audited once per process) and `liveHostConsented`. Read by the outbound door and, handed to its installer, by the socket guard (`engine/scripts/tooling/network-under-test.ts`).
- `pinned-process-internal.ts` — Compile the pinned-process profile from its declared input.
- `supervised-run.ts` — THE ONE TEST-RUN SUPERVISOR, used by both suites' runners and every nested runner a test launches: `superviseCommand` (a command under the native subreaper, `engine/guardian/test-process-supervisor.c` built by `engine/guardian/build.ts` `testProcessSupervisorBinary`: every descendant — detached, re-sessioned, orphaned — is killed when the command ends, is stopped or reaches its ceiling; a stop is SIGTERM first, within the suite watchdog's `killGraceMs` (`testExecution.webSuiteWatchdog` / `engineSuiteWatchdog`, exposed read-only), delivered once the supervisor announced its command; the supervisor leads its own process group, so a terminal's Ctrl-C is ONE stop, and a runner that dies stops it by its parent-death signal; an optional stall clock; a command reporting on its fd 3 keeps it, `--pass-fd`; `supervisedEndingLines` spells the killed-descendants and hard-ceiling lines for both runners), `runBoundedTestProcess` (the synchronous bounded launch, itself bounded: a supervisor that cannot close never hangs its caller) `readSupervisorReceipt` (the fd-3 receipt, CHECKED field by field), and `startDetached` (the ONE unsupervised background launch — a promotion's trigger: a new session, unreferenced, its stderr the caller's, an open log's, or nowhere). The web runner (`scripts/run-tests.ts` `superviseRun`) and the engine runner (`engine/scripts/tooling/recorded-command.ts`, the worker's launch) compose over it.
- `process-facts.ts` — THE one reader of process facts from procfs and of process liveness. Procfs is spelled once (`ROOT_POLICY.filesystemInfrastructure.procfsRoot`): `procfsPath`, `procfsDocument` (a document's text or `undefined`), and the named facts — the stat line (`parseStatLine`, parsed after the last `)`; `statFactsOf`), parent, group, `residentBytesOf`, the one boot clock and tick (`bootWallTimeMs`, `CLOCK_TICK_MS`, `startWallTimeMs`/`startWallTimeMsOf`), the listening TCP sockets and a process's socket inodes (read inside the owner; `parseListeningSockets` is the pure parse) and THE one "who listens on these ports" answer (`processesListeningOn`: the dev-server preflight, `scripts/sd.mjs` and `scripts/dev-stop.ts`; never an `ss`/`lsof` scrape), the mount table (`mountInfoDocument`), command line, working directory, executable, open-file targets, the pid table and ancestors. The recycled-pid-proof `ProcessIdentity` (`processIdentity`, `isProcessIdentityLive`: pid + start time; `processIdentityRecord`/`parseProcessIdentityRecord`: the one record a pid file holds — a bare pid is refused). The ONE liveness answer: `isProcessAlive` (EPERM = alive; a ZOMBIE is not alive: a killed orphan waiting on a subreaper that reaps late holds nothing), `isProcessGroupAlive`, `signalProcessGroup`, and the one terminate-poll-kill loop `terminate` (SIGTERM, the caller's grace, SIGKILL; a target is a pid, a `ProcessIdentity` — a recycled pid is never signalled, each signal re-checks — or a group). Never reads another process's environment (its secrets). Used by the checkout write door, the commit guard, the locks, the journals, the CPU reader, the mount-table reader, the cgroup diagnostics, the web suite's reaper, the process census, `scripts/sd.mjs`, the dev scripts (`scripts/dev-processes.ts`), the bench server and the tests' leak witnesses. `engine/test/prevention/process-liveness-owner.test.ts` refuses a `kill(<any target>, 0)` probe of any receiver, a direct procfs read and a process-list scrape (`ps`/`ss`/`pgrep`/`pkill`/`lsof`/`fuser`/`netstat` run as a command) anywhere else (engine, server, scripts, benches, every test tree), and a pid-addressed `process.kill(…, "SIGKILL")` in the product and its tooling (a private terminate loop's escalation), each declared exception with its reason.
- `instrument-lock.ts` — THE HOST'S ONE INSTRUMENT LOCK, on the one lock primitive (`src/filesystem/file-lock.ts`): every heavy instrument (a whole suite, coverage, a browser run, `ws validate`/`ws merge`, `harness slot run`) holds one lock file per host user (`testExecution.instrumentLock`, required: its place under the host user's cache folder — the password database's home, never `$HOME` or `$XDG_CACHE_HOME`; refused in a checkout or the keep-out floor — and the number of test files that make a run heavy). A second heavy run WAITS, naming the holder (`waitForInstrumentLock`, `holdInstrumentLock`); a run inside a hold (the holder, or a supervisor it adopted, is this process or an ancestor — read from the record's structured fields) borrows it; `instrumentLockStamp` reads "held"/"unslotted" from the live holder and the owner's acquisition token (`HARNESS_INSTRUMENT_LOCK_TOKEN`). The door every runner calls is `engine/scripts/tooling/test-run-lock.ts` `enforceTestRunLock`.
- `instrument-lock-adoption.ts` — the hold this process owns, and `adoptIntoOwnedInstrumentLock`: `superviseCommand` adopts every supervisor it starts into the owned hold, so a holder killed outright leaves the lock held until the supervisor (which ends only after its command's whole process tree is gone) has ended.
- `fault-policy.ts` — THE ONE PROCESS FAULT POLICY (SCALE-CR1 C2, SCALE-CR1-FIX H1/H2): `installProcessFaultPolicy({ role })`, called ONLY by three doors — the process bootstrap `bootstrapProcess({ role })` (`src/runtime/cli-debug.ts`: every CLI entry point and top-level program), the worker threads' prelude (the prelude half of `worker-bootstrap.ts`: every worker started through `bootstrappedWorker`), and the web server's first import (`server/kernel/process-fault-policy.ts`); `tests/prevention/guarded-callbacks.test.ts` refuses any other install and any `new Worker(` without the prelude. The ROLE decides: an uncaught exception is fail-stop everywhere (reported, recorded through the registered ledger lane — `registerFatalFaultRecorder`: the web server's `process-fault` event — and exit `PROCESS_FAULT_EXIT_CODE`, 70); an unhandled rejection or a guarded callback fault is counted and reported (the one always-on report, `reportAlwaysOn`; logarithmic per fault identity) — a SERVICE (`server`, `server-thread`) lives on, a TOOL (`cli`, `worker`) fails closed with a sticky exit 70 (its own `exit` listener restores it over a later 0), a process with NO role keeps Node's default (the fault is re-raised: a test runner fails the file — the suites' budget of 0). Every step is total. `guarded(owner, fn)` — THE EVENT LOOP'S DOOR — is defined here (the policy's own; no import cycle); `processFaultCounts`/`lastProcessFault`/`processFaultRole` feed the `process.faults.*` signals.
- `worker-bootstrap.ts` — the worker threads' bootstrap, both halves of one protocol: `bootstrappedWorker(entry, role, options)`, the arguments of every worker thread — `new Worker(...bootstrappedWorker(entry, role, options))` starts the thread on THIS module with its boot record (`WORKER_BOOT_KEY`: the entry and the role — `server-thread` for the database facade's supervised threads, `worker` for a pooled task) added to its `workerData`; `execArgv` untouched (an explicit list would replace node's own inheritance, and a worker refuses a parent's process-level options); and the PRELUDE half: in a thread started with a boot record it installs the fault policy for the role, then imports the real entry (an invalid record refuses to start the thread; imported as a library it does nothing) (SCALE-CR1-FIX H2).
