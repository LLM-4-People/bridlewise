# Git

The git domain: the read-only git port and the contracts the custody layer builds on.

## What each file does

- `git-adapter.ts` — the git-adapter module.
- `git-config.ts` — Git operational defaults — canonical owner for git-domain configurable.
- `git-port.ts` — the git-port module; also the ONE spelling of a full git object name (`GIT_OBJECT_NAME_PATTERN`, anchored as `GIT_OBJECT_NAME`: SHA-1 or SHA-256 hex), which every object-id check in the engine imports.
- `declared-deletions.ts` — the DECLARED-DELETION primitive: a deliberate deletion the commit guard's move-loss check would refuse (its exact bytes also sit at an ignored path: a `.bkp/` backup, a frozen snapshot, a leaked fixture) is declared first. `declareDeletions` (`harness deletions declare <path>…`, the `workspaceGit.declareDeletion` action) records each literal path with the blob HEAD holds there, HEAD, HEAD's move count (`headMoves`) and the blob's IGNORED COPIES at declare time (`ignored-copies.ts`), in the checkout's OWN git directory (`--git-path bridlewise/declared-deletions.json`, never the tree or the index); a folder, a pattern, a second spelling or a path with anything still on disk is refused, all or nothing, with a typed code, and a checkout with no HEAD reflog is refused (`declared_deletion_head_unlogged`). `judgeDeclaration` (the guard, reading the record, HEAD and its moves from the git being committed) accepts a staged deletion only for the same path, the same blob, an unmoved HEAD (same commit AND same move count, so a `reset --soft` back is still stale), a path still absent, only recorded copies, and this git directory; otherwise it names the verdict (`undeclared`, `mismatched`, `stale`, `expired`, `copies-changed`, `foreign`; `DECLARATION_REFUSAL_CODES`); `declarationState` is the one rule the guard and the status share. Every change to the record is one read-modify-write under the one cross-process file lock (`<record>.lock`). `consumeDeclaredDeletions` (the `post-commit` hook) removes the declarations whose path HEAD no longer holds or whose path is on disk again; `clearDeclaredDeletions` (`harness deletions clear`) withdraws all; `declaredDeletionsStatus` / `declaredDeletionsSummary` (`harness deletions status`, the `workspaceGit.declaredDeletions` signal) never write. Every declaration, acceptance, refusal, consumption, expiry and withdrawal is an audit event.
- `ignored-copies.ts` — the pairing the move-loss rule and a declaration share: `blobSizes` (one `cat-file --batch-check`), `carriesLosableContent` (the empty blob identifies nothing), `movedIntoIgnored` (content, not name; never a deletion's own path) and `ignoredCopies` (the pairing asked of one checkout, in a given git environment: the machine-local ignored population, size-filtered, then hashed).
- `checkout-state-record.ts` — the ONE reader and writer of the checkout-state records (the index baseline, the deletion declarations): `readCheckoutStateRecord` (`null` when absent; the caller's typed refusal for an unreadable, non-JSON, schema-failing or digest-mismatched record) and `writeCheckoutStateRecord` (digest computed, canonical JSON, the atomic writer at the private-state mode).
- `index-baseline.ts` — the live index's protected staged blobs (the ones HEAD does not hold), recorded in `ROOT_POLICY.verification.liveIndexBaseline.path` and pinned by a ref under `…pinRefNamespace` so `git gc` keeps them: `recordIndexBaseline` (candidate create, `harness index record`), `indexBaselineDrift` (read-only: held, superseded by a commit, or LOST — `harness index status`, the `workspaceGit.liveIndexState` signal and the commit guard, which never write) and `checkIndexBaseline` (the same, advancing the record when HEAD moved with nothing lost — `harness check`'s `live-index` step and every candidate command), `assertIndexAtBaseline`, and `repairIndexToBaseline` (`harness index repair`: re-stages only lost entries in one `update-index -z --index-info`, refuses a missing blob first, never removes an entry, never reverses a commit). The repair is returned as the verb `harness index repair`, never a script path.
- `index-entries.ts` — the ONE `git ls-files --stage` reader: `IndexEntry`, `parseIndexRecords` (also fed by the candidate manifest's pinned git, `engine/scripts/tooling/candidate-manifest.ts`), `indexEntries(root, environment)` and `intentToAddPaths` (the `git add -N` entries, which `ls-files --stage` shows unflagged).
- `workspace-lifecycle.ts` — the workspace-lifecycle module.
- `worktree-port.ts` — the worktree-port module; `configuredWorktreeGitPort` and `configuredGitRepository` (the same configured executable and inspect ceiling, for the tree readers) are the ONE construction of the repository's git.
- `tree-reader.ts` — the tree readers (`commitTreeReader`: one `ls-tree` and batched `cat-file`, binary-safe, a non-UTF-8 path refused; `workingTreeReader`: what `git add -A` would commit) and writers (`writeBlob`; `writeTree`: a private index per call, the written tree read back and compared, `tree_writer_mismatch`), all through ONE door, `gitOutput`, over a `GitRepository` (the configured executable, each call bounded).
- `repository-ownership.ts` — the small git reads the checkout-state records share: `gitAcceptsRefName` (the ONE ref-syntax check); `requiredRepositoryToplevel` (typed refusal outside a work tree), `gitPath` (git's own `--git-path` answer; `indexFilePath` is its `index` case), `headCommit` (`null` on an unborn branch), `headMoves` (the HEAD reflog's length: equal readings mean HEAD never moved in between, even when it came back) and `headVersions` (HEAD's mode and object for exactly the asked paths: `ls-tree` paths are patterns that DESCEND, so a folder asked with a file under it is asked on its own and only asked paths are kept); and `GitEnvironment` (`inherited`: a hook's `GIT_*` are the answer; `directory`: git asked about a directory alone — a question about another place than the hook's repository, e.g. the commit guard locating its engine in a linked worktree), `indexFilePath` (the ONE "which index file" answer), `gitNulRecords` (strict `-z` records), and the ONE reader of "which files does the repository own": tracked, present-tracked (an unstaged deletion is absent, `presentTrackedFiles`), owned (tracked plus untracked-not-ignored), tracked-but-ignored populations under the VERSIONED `.gitignore` rules only (never `.git/info/exclude` or global excludes) — with ONE declared exception in the reader, `machineIgnoredFiles` (what `git add -A` skipped on THIS machine, `--exclude-standard`: the move-loss population) — strict UTF-8, `undefined` outside a work tree; `repository-ownership-reader.test.ts` refuses any other `git ls-files` population query.
- `working-copy.ts` — the ONE working-copy builder: copies what a checkout owns (optionally narrowed, plus named ignored paths such as pinned build outputs) into a private directory with its OWN git — objects borrowed read-only from the CANONICAL store (never another copy's), the source HEAD, remotes and upstreams, and either a mirror of the source index, every change staged with git's own ignore view (`stage-all`), or the index itself materialized (`staged`, the commit guard's view: any index file the caller names — the hook's `GIT_INDEX_FILE` — minus its intent-to-add entries, exactly what the commit records) — so git questions in the copy are answered by the copy; also `workingCopyDifferences` and `refreshWorkingCopy` (which never touches the paths the copy authors); `stageInCopy` (the one staging door in a copy: `add` against a private object directory, absorbed afterwards — the borrowed store is never freshened and the alternates never edited); and `snapshotWorkingTree` (the ONE snapshot of a dirty tree as a tree, a commit and an optional ref, without touching the real index or freshening the store; `advanceHead` moves HEAD by compare-and-swap from the snapshot's parent — `snapshot_head_moved` when a commit landed meanwhile — and only when the real index records the tree; a name is recorded only after every refusal passed, must be a ref git accepts, and never the checked-out ref).
