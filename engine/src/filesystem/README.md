# Filesystem

The engine's filesystem boundary: atomic writes, path-boundary and link-containment checks, Linux path traversal, and the durable/pinned-path contracts that keep file access inside the allowed roots.

## What each file does

- `atomic-write.ts` — the atomic-write module: THE one write-temp-then-rename owner for the engine AND the web server (the server's copy was deleted): every generator, the transactional editor, the server's config writer and editor bridge; it asks the checkout write door first (a refusal throws, before anything is written); `createMode` (0o666 = a plain write), `createParentDirectories`, `durable` (every fsync fatal, the directory's too) and `exclusive` (published with `link(2)` only under a free name: never observable half-written, a failed write leaves nothing), and a failure always carries its `error`. A final-component symbolic link is followed ONLY when its target lies, by (device, inode), inside a root the caller declares for that write kind (`linkTargetRoots`: the config's own directory, the project root); a link elsewhere is `atomic_write_link_refused`, a dangling link or loop `atomic_write_link_unresolved` — typed, never a raw ENOENT, never written through.
- `move-path.ts` — THE one owner of move operations (`movePath`: an atomic rename on one filesystem, a verified copy-then-remove across devices; typed `move_did_not_land`), used by the web server's editor, database files and key tool. A move writes two places, so BOTH its source and its destination are asked of the checkout write door. Replacing a file's contents is the atomic-write owner's.
- `journaled-commit.ts` — THE one multi-file transaction (`commitJournaled` / `recoverJournaledCommit`): a journal, previous/next copies staged beside each target, renames, a caller `verify` with the backups still on disk (a throw rolls back), then cleanup; a crash is recovered by the next run (pending → rolled back, verified → completed) — but never while the journal's OWNER (pid + start time) is still running (`in-progress`, untouched), and the owner re-reads its journal and targets before marking `verified` (`journaled_commit_preempted` instead of a false success). Journals live at `<root>/.bridlewise/state/journals/<name>.json` (`journalPathFor`, `journalsUnder`; callers pass a name), are published complete (durable + exclusive through `atomicWriteFile`: never observable empty, a full disk leaves nothing) and must describe their own transaction (the id is the hash of the OWNER and the plan — a retry of the same plan by another process has its own staged names — every staged name derived from it) or they are a typed refusal; recovery runs under the journal's own file lock (concurrent recoverers take turns; the second finds nothing to do), removes a journal only while it still names its transaction, treats a journal that vanished since the listing as gone (never `unreadable`), trusts `verified` only when every target holds its next bytes (`journaled_commit_verified_mismatch`, every staged copy kept), and makes the renames durable (target folders fsynced) before `verified`; a rollback verifies every backup before restoring any (`journaled_commit_backup_invalid`, tree untouched; an unreadable backup or target is typed, never a raw EISDIR) and restores the base mode the journal RECORDED (permission bits only); every fsync — the `verified` mark and the rollback restores included — is fatal; rollbacks and recoveries are audit events, heard in every process (the server's debug bridge; every engine CLI entry point runs `bootstrapProcess`, `src/runtime/cli-debug.ts`). Used by the test inventory and the candidate copy-back.
- `checkout-write-door.ts` — the checkout write door: a process under test never writes a file of the checkout it tests outside that checkout's writable directories (`.bridlewise/`), the checkout identified by realpath and device/inode, a planted `.git` carving out nothing (`generator_live_checkout_under_test`). "Under test" is decided once at load from facts, never from argv strings: our runners ARM the checkout (`armCheckoutUnderTest`: the engine test worker, the root `vitest.config.ts`) — an inherited marker variable plus a marker file each armed process holds open; this process's own node command line (`process.execArgv`/`argv`: `--test`, a test-file script, a test file in a preload or eval code); and the ancestors through procfs (a held marker descriptor, or a node runner's command line) — no ancestor's environment is ever read. The names come from `ROOT_POLICY.verification.checkoutWriteDoor`; without procfs it warns loudly (`HARNESS_CHECKOUT_DOOR_PROCFS_UNAVAILABLE`). Decided without git, so the web server's graph gains no process spawn.
- `persisted-key.ts` — admits one opaque root key from a passphrase or a private binary key file in the KEY HOME (`self-protection/key-home.ts`: `<digest of the database folder>.key`, 0600, published once, never replaced — never beside the database), and registers the database as a harness store. Whether a missing key may be minted is its store's decision (`disposition`: the web database refuses only when it holds ciphertext at v5+, a timeline only when it holds sealed originals); an install whose old key still sits beside its database is only ever loaded (moved by the key tool, never re-keyed). A passphrase is stretched over a RANDOM per-database salt kept beside where the key would be, with the same publication; a database from before random salts that holds ciphertext adopts the old fixed salt (`adopt-fixed-salt`, decided by its store) until the re-key tool retires it. Every key is published through ONE writer (`publishKeyMaterial`: complete and fsynced before its name exists, the folder fsynced after). A missing key for an existing database is refused naming that database's path and, when its old key still sits beside it, the exact relocation command; a staged next key (an unfinished re-key) refuses every open (`persisted_key_rekey_in_flight`).
- `path-identity.ts` — THE ONE owner of where a path really is: `resolveLocation` (the only minter of `ResolvedAbsolutePath`), `identityKey`, and `(dev, ino)` ancestry that holds for places created later and compares names case-insensitively on a Windows drive.
- `database-files.ts` — the names of one database's files (the database, SQLite's companions, pre-migration and pre-re-key copies, staging copies a crashed copy left), shared by the copy writers and the keep-out list: `databaseFamily` names the whole family ONCE by prefix (`web.db*`, `db-key*` in its folder), and `legacyInstallIn` recognises an install still keeping its key beside its database with no registration (a key-sized `db-key` beside a SQLite file; the key's bytes are never read); `findLegacyInstalls` walks roots for them (every depth, the one skip list, at most a folder budget — `truncated` when it stops there) and `UNLISTABLE_DIRECTORY_CODES` is the one classification of a folder that cannot be listed, shared with the keep-out list's walk. The caller explicitly selects create-or-load, load-only or adopt after admitting its store state.
- `sqlite-wal.ts` — THE WAL journal owner: `establishWalJournal` enters WAL mode past a fresh file's concurrent first openers (SQLite refuses one of them SQLITE_BUSY without the busy handler; the owner waits for the other opener through the busy handler, within the same timeout), and `checkpointSqlite` reports a checkpoint from its own result row (a failure or an incomplete TRUNCATE is reported centrally; an incomplete PASSIVE, the normal outcome with readers, is not).

- `private-state.ts` — the private-state modes (from `ROOT_POLICY.filesystemInfrastructure.privateState`) and `ensurePrivateStateDirectory`, the one creator every harness state directory goes through; generic writers never choose a directory mode. Also THE ONE owned-temporary rule: every temp file or directory a process leaves beside shared state carries its owner (`<pid>-<start time>`) and a nonce of `privateState.temporaryRandomBytes` — `ownedTemporaryName` (`<prefix><pid>-<start>-<nonce>`), `ownedSiblingTemporaryName` / `isOwnedSiblingTemporary` (`.<target>.<kind>-<pid>-<start>-<nonce>.tmp`, beside the file it is published over; a target too long for `NAME_MAX` is named by its digest — the atomic writer's temps are this form, kind `write`), `ownedTemporaryOwnerOf` / `isOwnedTemporaryLive` (THE one parse of both forms, for listers: owner, kind, live or dead), `abandonedSiblingTemporaries` / `sweepAbandonedSiblingTemporaries` (the first write of a process into a directory removes what dead writers left beside their targets, never a live writer's), `createOwnedTemporaryDirectory` (the one replacement for `mkdtemp`; dead owners swept first), `abandonedTemporaries` / `sweepAbandonedTemporaries` (an audit event) — used by the atomic writer, the durable filesystem, the immutable receipts, the persisted key, the lock stagings, the commit guard, the snapshot, the guardian's per-spawn and probe directories and the compile-cache probe; the lock owners (the file lock, the resource lock, the test-run lock) judge a holder by pid AND start time. `engine/test/prevention/owned-temporary-owner.test.ts` refuses the old shapes.
- `file-lock.ts` — THE one cross-process file lock: `withFileLock` (synchronous bounded wait, re-entrant), `acquireFileLock` (asynchronous bounded wait) and `tryAcquireFileLock` (never waits). The holder's record is published by `link(2)` through the one exclusive writer; a LIVE holder (pid AND start time — a record or adopted entry without a start time is no identity, so it is unreadable) is never broken, whatever its age; the lock file is read without following a link, without blocking and within `fileLock.maximumRecordBytes`, and a holder label is read back escaped and bounded (`printableHolderLabel`); a dead holder's lock is broken at once and ATOMICALLY (under `<lock>.break`, only while it still holds the exact record judged, so two breakers never both proceed); an unreadable lock file is honoured until the caller's bound (default `ROOT_POLICY.filesystemInfrastructure.fileLock.staleMs`), then broken; nonce-checked release, release at exit; every break and timeout is an audit event (`file-lock-broken`, `file-lock-timeout`). Consumers own only where their lock lives and the error it maps to: the config write lock, the deletion declarations, the run ledgers (`src/shared/run-history.ts`), the resource locks (`src/workflow/resource-lock.ts`), the test-run lock (`scripts/tooling/test-run-lock.ts`) and the merge-round script.
- `temporary-root.ts` — the system temp root's headroom (`temporaryRootHeadroom`: free bytes AND inodes as shares; `temporaryRootPreflightLine`): both test runners print it before a run and warn — never refuse — under `ROOT_POLICY.filesystemInfrastructure.temporaryRootMinimumFreeFraction`.
- `database-provenance.ts` — A TEST NEVER OPENS A REAL DATABASE (UD-S15): the product stamps a database it opens for writing (SQLite `application_id`, `DATABASE_PROVENANCE.product`); a process under test refuses a stamped one (`admitDatabaseProvenance`, `database_real_under_test`) at the web client and the timeline store (`createTimelineStore`, `migrateTimelineFile`, `pendingTimelineMigrations`), by the file's own header — and an UNSTAMPED one that already holds tables outside the run's temporary root (a real database from before the stamp, SCALE-CR1-FIX N5), while an empty one a test creates is stamped `DATABASE_PROVENANCE.test`; the fixture door restamps its copies (`markFixtureCopy`); `databaseProvenanceOf` reads the stamp (the health route's `database`).

## Persistent key publication

File keys require a regular 32-byte file with the existing private-state mode, including absence of special permission bits. New keys use a complete private stage, descriptor mode admission, full write and sync, then a no-overwrite hard link. Competing creators reread the winner; only ENOENT permits creation and EEXIST permits convergence. Every successful reader syncs its admitted file and parent directory, including a contender that reads before the publisher's directory sync. Cleanup removes only the caller's stage. Existing/read-only encrypted stores cannot mint replacement keys. Passphrase precedence and the existing scrypt salt remain exact format requirements.

The key and SQLite migration are separate effects: a failed migration can leave a valid published key for retry. This owner does not establish hostile parent-path custody, key rotation, cross-resource atomicity or a per-event fsync receipt. A successful checkpoint result describes SQLite progress; a configured timer interval is best-effort cadence rather than a maximum crash-loss window.
